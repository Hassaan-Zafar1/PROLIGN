3. THE TESTING PYRAMID — WHAT "UNIT / INTEGRATION / E2E" MEANS HERE
=====================================================================

  UNIT TESTS
    Test one small piece of pure logic in complete isolation - no network,
    no database, no other files involved. Fastest, most precise.

  INTEGRATION TESTS
    Test a full request going through the real app: route -> controller ->
    service -> database, but the "database" is a fake in-memory one and
    external services (Groq AI, Stripe, Slack) are mocked. Confirms the
    pieces work together correctly, without needing the real servers/keys.

  END-TO-END (E2E) TESTS
    Drive the actual app the way a real user would: a real Chrome browser,
    against the real frontend dev server and the real backend, clicking
    real buttons. Slowest, but the closest thing to "does this actually
    work for a user."

4. HOW TO RUN EACH TYPE OF TEST MANUALLY (commands)
=================================================

All commands below assume PowerShell, starting from the project root
(C:\Users\user\Desktop\PROLIGN) unless a "cd" is shown.

  ---------------------------------------------------------------
  A) BACKEND INTEGRATION TESTS (Node, Vitest + Supertest)
  ---------------------------------------------------------------
  cd backend

  npx vitest run                       # run all 122 tests once, then exit
  npx vitest run --coverage            # same, plus a coverage report
  npx vitest run auth.test.js          # run just one file
  npx vitest run -t "TC-AUTH-011"      # run just one test by name

  npm test                             # opens Vitest's interactive WATCH mode
                                        # (stays running, re-runs tests as you
                                        # edit files - press "q" to quit).
                                        # Use "npx vitest run" instead for a
                                        # single pass that exits on its own.
  npm run test:coverage                # same as "npx vitest run --coverage"

  Reports land in: backend/reports/ (JUnit XML) and
  backend/reports/coverage/index.html (open this in a browser for a
  clickable, line-by-line coverage report - good for a demo).

  ---------------------------------------------------------------
  B) AI-SERVICE INTEGRATION + UNIT TESTS (Python, pytest)
  ---------------------------------------------------------------
  Each Python service has its own virtual environment - activate it first.

  AI_interviewer (25 tests):
    cd backend\AI_interviewer
    venv\Scripts\Activate.ps1
    pytest                              # runs everything, with coverage
    pytest tests\test_routes.py -v      # just the route tests, verbose
    pytest -k "TC_AI_001"               # run a test by name pattern
    deactivate                          # when done

  Rag_Chatbot (38 tests):
    cd backend\Rag_Chatbot\app
    venv\Scripts\Activate.ps1
    pytest                              # runs everything, with coverage
    pytest tests\test_routes.py -v
    pytest tests\test_http_client_and_key_pool.py -v   # just the unit tests
    deactivate

  Reports land in: reports/junit.xml and reports/coverage/index.html
  inside each service's own folder.

  ---------------------------------------------------------------
  C) FRONTEND E2E TESTS (Playwright, real browser)
  ---------------------------------------------------------------
  cd frontend

  npx playwright test                  # run all 11 tests, headless, parallel
  npx playwright test --workers=1      # run serially (steadier, slower)
  npx playwright test --headed         # SHOW the browser while it runs -
                                        # best option for a live demo
  npx playwright test --debug          # step through one action at a time
  npx playwright test e2e\tests\login.spec.js   # just one file

  npx playwright show-report           # opens the last HTML report in
                                        # your browser (screenshots/video
                                        # on failure, full trace viewer)

  Note: Playwright auto-starts the frontend dev server for you. The
  backend must already be running separately (npm run dev in backend/)
  since the E2E tests talk to the real API.

  ---------------------------------------------------------------
  D) FRONTEND UNIT TESTS (Vitest + React Testing Library)
  ---------------------------------------------------------------
  cd frontend

  npx vitest run                       # run all 133 tests once, then exit
  npx vitest run --coverage            # same, plus a coverage report
  npx vitest run src/utils             # just the pure-function tests
  npx vitest run src/components/common # just the UI component tests
  npx vitest run src/utils/mentorLevel.test.js   # just one file

  npm test                             # opens Vitest's interactive WATCH
                                        # mode (same caveat as backend's -
                                        # press "q" to quit)

  Reports land in: frontend/reports/unit-junit.xml and
  frontend/reports/coverage/index.html (open in a browser).


5. WHAT EACH NEW FILE / FOLDER IS FOR
=================================================

  --- frontend/src/test/  (shared unit-test infrastructure) ---
  test/setup.js               Wires up two things every unit test needs:
                             jest-dom's extra matchers (toBeInTheDocument,
                             toHaveClass, toBeDisabled, ...) and automatic
                             DOM cleanup between tests (without this,
                             components from an earlier test in the same
                             file stay in the page and the next test finds
                             duplicates).
  vitest.config.js            Updated to point at that setup file and to
                             use jsdom (a fake browser environment) so
                             component tests can run without a real browser.

  --- frontend/src/utils/*.test.js, routes/routeConfig.test.js  (pure-logic
      unit tests - no rendering, no network, fastest tests in the repo) ---
  mentorLevel.test.js          Tests the mentor-experience-level calculation
                             (junior/intermediate/senior by registration date).
  profileCompletion.test.js    Tests the "profile X% complete" calculation.
  flattenProfile.test.js       Tests the mentor/mentee data-reshaping logic
                             that bridges the backend's nested profile shape
                             to the flat shape the dashboards expect.
  errorHandler.test.js         Tests which user-facing message gets shown
                             for each kind of API error (mocks the toast
                             library so no real UI popup happens in tests).
  tokenManager.test.js          Tests the login-token storage wrapper.
  routeConfig.test.js           Tests the page-key <-> URL-path translation
                             layer described in Section 2/6.

  --- frontend/src/components/common/*.test.jsx  (component unit tests -
      React Testing Library renders each component alone, no network,
      no router, no other components involved) ---
  One test file per shared UI building block used across the whole app:
  Avatar, Badge, Button, Card, EmptyState, ErrorBoundary, Input, KpiCard,
  Modal, Select, Textarea, Toggle. Each file checks that component's own
  behavior in isolation (e.g. Button.test.jsx checks that clicking calls
  onClick, that "loading" disables it and shows a spinner, etc.) - if one
  of these breaks, every page that uses that component would be affected,
  so this is a highly leveraged place to have tests.

  --- frontend/e2e/  (Playwright E2E suite) ---
  playwright.config.js       Playwright's main config: reporters, retries,
                             screenshots/video on failure, auto-starts the
                             dev server.
  e2e/global-setup.js        Runs once before the whole suite: makes sure a
                             known admin test account exists.
  e2e/pages/*.js  (11 files) "Page Objects" - one file per app screen
                             (LoginPage, BookingPage, AdminDashboardPage,
                             etc). Each wraps that screen's buttons/inputs
                             so tests read like plain English instead of
                             raw CSS selectors.
  e2e/fixtures/base.js       Wires all the page objects together so every
                             test can just ask for the ones it needs.
  e2e/fixtures/apiHelpers.js Direct backend API calls used for fast test
                             SETUP (e.g. "create a verified mentor
                             account") so tests don't waste time clicking
                             through registration when that's not what's
                             being tested.
  e2e/data/users.js          Generates unique fake user data per test run
                             (unique email/name each time, so tests never
                             collide with each other's leftover data).
  e2e/data/sampleCv.js       Builds a tiny valid PDF file in memory, used
                             to test CV upload without needing a real file
                             on disk.
  e2e/tests/*.spec.js (7)    The actual tests. 6 are the real user
                             journeys (guest-browsing, login, admin,
                             booking, mentor-signup, mentee-signup); smoke.
                             spec.js is a minimal "does the app load at
                             all" sanity check from Phase 0.

  --- backend/test/  (shared test infrastructure, not tests themselves) ---
  test/globalSetup.js        Starts one fake in-memory MongoDB for the
                              whole test run (so tests never touch your
                              real database).
  test/setup.js               Connects each test file to that fake database
                              and wipes it clean between tests; also makes
                              sure no test ever sends a real email.
  test/helpers.js             Shortcuts for common setup ("create a
                              verified mentee/mentor/admin account and log
                              them in") reused across all 14 test files.
  test/sampleCv.js             Same PDF-generator idea as the frontend one,
                              for backend CV-upload tests.
  backend/*.test.js (14 files) One file per API area (auth, admin, sessions,
                              payments, reviews, etc.) - 122 tests total.
  backend/vitest.config.js    Vitest's config: coverage thresholds, JUnit
                              reporting, runs test files one at a time
                              (needed since they share the one fake
                              database).

  --- backend/AI_interviewer/ and backend/Rag_Chatbot/app/ (Python) ---
  conftest.py (root)          Makes the fake in-memory MongoDB swap-in
                              happen BEFORE the app code ever loads (has to
                              happen this early or it's too late).
  tests/conftest.py            Wipes the fake database clean between tests.
  tests/test_health.py         Original Phase 0 smoke test ("does the
                              service start at all").
  tests/test_routes.py         The real per-route test suite (24 tests for
                              AI_interviewer, 16 for Rag_Chatbot).
  tests/test_http_client_and_key_pool.py,
  tests/test_groq_client_parsing.py
                              (Rag_Chatbot only) Pure unit tests for the
                              retry/rate-limit/API-key-rotation logic and
                              the AI-response parsing logic.
  pytest.ini / .coveragerc     Pytest config: coverage thresholds, report
                              locations, which folders to ignore.

  --- qa/  (the actual deliverables) ---
  TEST_PLAN.md                 The test plan document (Section 1).
  test_cases_testrail_import.csv   130 test cases, import into TestRail.
  bugs_jira_import.csv         38 bugs — source CSV, already created live in
                              Jira via API this session (see Section 8).

  --- .claude/skills/  (not test files - guidance for future test-writing) ---
  testing-strategy, vitest, supertest, playwright, pytest / SKILL.md
                              Short reference docs so that future test
                              writing (by you, a teammate, or an AI
                              assistant) follows the same conventions
                              already established here, instead of
                              reinventing the pattern each time.

  --- .github/workflows/ci.yml ---
  A GitHub Actions pipeline scaffold that would run all of the above
  automatically on every pull request (frontend tests, backend tests, both
  AI services, E2E). Not yet turned on - needs repo secrets configured
  first.


6. REAL BUGS FOUND AND FIXED WHILE BUILDING THIS (not just theoretical)
=================================================
These were caught by the automated tests actually running against real
code, not found by reading code alone:

  1. Mentor CV upload crashed with a 500 error on every single real
     request (a PDF-library incompatibility). Fixed in
     backend/services/pdfTextService.js.
  2. The AI interview service's mentee CSV export crashed every time any
     completed profile existed. Fixed in
     backend/AI_interviewer/services/interview_service.py.
  3. The backend's login rate-limiter had no separate dev/production
     setting, so normal testing activity was getting blocked with 429
     errors. Fixed in backend/routes/auth.js.
  4. A Playwright test flakiness bug: a booking test occasionally failed
     because it never explicitly clicked a time slot before continuing -
     fixed the test itself, not the app, but worth mentioning as a real
     "test correctness" catch.

These four are why "writing tests" caught real, shippable problems - not
just busywork.

  The 4 CRITICAL open bugs (recommend fixing before/alongside filing them,
  not just tracking them):

  1. Real production database password is hardcoded as a fallback value
     in source code that's committed to git. Recommend rotating that
     database password regardless of when the Jira ticket gets worked.
  2. The "record a payment" API endpoint trusts whatever amount and status
     the client sends - a user could record a fake "paid" transaction
     without any real Stripe payment happening.
  3. The "book a session" API endpoint trusts whatever price the client
     sends instead of using the mentor's real listed price - someone
     could book a session for $0.
  4. The AI interview completion endpoint saves data under field names
     that don't exist in the database schema, so most of what a mentee
     enters during their interview is silently thrown away.

  The other 34 (10 High, 15 Medium, 1 Low) span frontend UI bugs
  (e.g. a whole Analytics page that crashes for mentors/admins), backend
  API bugs (e.g. logging in with a Google-only account crashes instead of
  showing an error), and database bugs (e.g. two services disagreeing on
  whether a field should be unique, missing indexes on frequently-searched
  fields, deleting a user leaves orphaned records behind).
